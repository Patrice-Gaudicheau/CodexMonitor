# Development and verification

User installation instructions are in [INSTALLATION.md](INSTALLATION.md). This document covers the v1.2.0 implementation and developer tools. Dated results and hardware limitations are in [TEST-RESULTS.md](TEST-RESULTS.md).

## Architecture

CodexMonitor is a C# / .NET 10 Windows Forms application using the documented native `Shell_NotifyIcon` integration. It has no third-party application packages or localization framework.

| Location | Responsibility |
| --- | --- |
| `src/CodexMonitor.Core` | Quota parsing, selection, freshness, and presentation data. |
| `src/CodexMonitor.Core/Resources` | Embedded French and English strings, accessed through `Localization` and `UiText`. |
| `src/CodexMonitor` | App Server transport, GDI+ badge, native tray integration, details window, menus, and preferences. |
| `tests/CodexMonitor.Tests` | Standalone tests, including a simulated App Server; no external test framework. |
| `scripts` | Build, test, and published-executable verification tools. |
| `docs/protocol` | Selected schemas generated from the inspected native CLI version. |
| `CodexMonitor.sln` | Application, core library, and test projects. |

The details window uses mint accents, rounded cards, a circular indicator, Segoe UI fonts, and a native refresh button. GDI+ draws the cards, indicator, and badge at runtime; no external graphic asset or WebView is required. Windows Forms uses `PerMonitorV2`. The [UI redesign record](UI-REDESIGN.md) describes the original French design; [LOCALIZATION.md](LOCALIZATION.md) describes language selection and live updates.

## Codex App Server integration

The application starts its own `codex app-server --listen stdio://`, independent of the Codex desktop interface. `CodexLocation` resolves a Windows executable first, then optionally a WSL launch command when Windows Codex is absent. A Windows connection or authentication failure never triggers fallback. An explicit invalid Windows path fails closed. After `initialize` / `initialized`, it requests only **`account/rateLimits/read`**. It does not initiate conversations or inference, use a private API, or read authentication tokens manually.

WSL uses the system `wsl.exe`, the default distribution (or `CODEX_MONITOR_WSL_DISTRIBUTION`), a home working directory, and `/bin/sh`'s login environment. Profile output is redirected to stderr to preserve JSONL stdout. `CODEX_MONITOR_WSL_CODEX_PATH` can supply an absolute Linux path outside that environment's `PATH`; it is passed as a positional argument, never interpolated into shell code. A Windows `CODEX_HOME` is cleared before the Linux profile runs. Native and WSL commands share the same transport, timeout and protocol restrictions.

The integration was checked against schemas generated by the inspected CLI (`codex-cli 0.159.0`) and the [official App Server documentation](https://learn.chatgpt.com/docs/app-server#6-rate-limits-chatgpt). The checked-in schema excerpts are [InitializeParams.json](protocol/InitializeParams.json) and [GetAccountRateLimitsResponse.json](protocol/GetAccountRateLimitsResponse.json). Authentication is handled by the CLI's normal mechanism.

Quota rules:

- `rateLimitsByLimitId` is authoritative when available, including an empty map. The legacy `rateLimits` view is used only when the map is unavailable.
- Normal windows use `remaining = clamp(100 - usedPercent, 0, 100)`. Badge fractions are rounded down. Missing values remain unavailable.
- Individual budgets use their supplied `remainingPercent` directly. Credit information is shown separately without inventing a percentage.
- Automatic selection prefers the `codex` category, then its five-hour window, weekly window, and other available windows. Additional categories and both windows of a category are exposed in the menu.
- Labels follow actual duration: a `primary` window can be weekly. An explicitly selected quota that disappears remains unavailable until another selection is made.
- Reads occur at startup and about 60 seconds after the previous read finishes. A read has a 25-second timeout. Failures do not cause a tight retry loop; a new connection is created on the next attempt.
- The badge becomes a gray dash on a read error, after three minutes without a valid reading, or at the supplied reset time. Reaching a reset time does not imply 100% remaining.
- The tray tooltip is capped at Windows' 127-character limit; the details window exposes information that does not fit.

Protocol identifiers, JSON fields, quota keys, configuration identifiers, and externally supplied names retain their identity in both interface languages.

## Settings and process lifetime

`%LOCALAPPDATA%\CodexMonitor\settings.json` stores `SelectedQuota`, `Language` (`automatic`, `fr`, or `en`), and `AllowWslFallback` (default `true`). Missing, null, or unrecognized language values select Automatic. The existing v1.0.0 settings format remains compatible. Writes use a temporary file and atomic replacement; no separate configuration file is needed. The WSL checkbox saves before reconnecting, clears previous quota data, and is disabled during an active read.

Normal operation does not persist quota readings, authentication tokens, account identifiers, or raw logs. App Server stderr is drained without retention. Server errors are reduced to a code and a localized explanation to avoid displaying sensitive server text.

A user-specific mutex in the current Windows session rejects duplicate instances with exit code `10`. A Windows Job Object terminates the Windows App Server or WSL launcher and its Windows descendants when the monitor closes or is forcibly terminated. Linux processes are outside Windows jobs: disposal first closes stdin and allows up to two seconds for the Linux App Server to exit on EOF before terminating the launcher. The optional WSL tests check Linux fixture cleanup on normal disposal, canceled initialization, and an abrupt Windows owner exit. The tray icon is recreated on `TaskbarCreated`, and its size is recalculated for the taskbar resolution.

Startup is opt-in. The menu writes the quoted current executable path to `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `CodexMonitor`. Keeping that path when replacing the EXE preserves startup registration. No administrator access is needed.

## Build and publish locally

Use Windows and native PowerShell with the [.NET 10 SDK](https://dotnet.microsoft.com/en-us/download/dotnet/10.0) specified in [global.json](../global.json): **10.0.401**, with `latestPatch` roll-forward. Run commands from the repository root:

```powershell
dotnet build .\CodexMonitor.sln -c Release
.\scripts\Test.ps1
.\scripts\Test.ps1 -Live
.\scripts\Test.ps1 -Wsl
.\scripts\Test.ps1 -LiveWsl
.\scripts\Build.ps1 -OutputDirectory .\dist\v1.2.0\win-x64
```

`Test.ps1` uses a project-local SDK home and NuGet cache (`.dotnet-home`, `.nuget`). `Build.ps1` uses the same locations. The first restore needs NuGet access for .NET publishing components. After a successful restore, add `-NoRestore` to these two scripts to reuse the cache.

The offline suite covers CLI priority, disabled/missing WSL, invalid overrides, literal launch arguments, settings compatibility, and the localized checkbox. `-Wsl` additionally requires a usable default WSL distribution and exercises a local simulated Linux App Server, including paths with spaces and shell metacharacters, cancellation, missing CLI and cleanup. `-LiveWsl` adds a real quota read through WSL with Windows CLI absence simulated in the resolver; it needs a signed-in Linux CLI and network access. Neither option changes installed CLIs or saved user preferences.

The output is a self-contained Windows x64 **single executable**, about 111 MiB including the runtime. `PublishSingleFile`, `SelfContained`, and `IncludeNativeLibrariesForSelfExtract` are enabled, with embedded debug information. The build script checks that the distribution folder contains exactly one file; no application resource satellite DLLs are required. Native components may be extracted to the Windows temporary directory on first launch.

The default `Build.ps1` output is `dist/win-x64`. Specify `-OutputDirectory` as above to prepare v1.2.0 separately from retained earlier executables. `Build.ps1 -Arm64` supports optional cross-publishing to `win-arm64`; it has not been verified on ARM64 hardware. Local .NET publishing builds an artifact and does not create a GitHub Release.

## Verify the standalone executable

Pass the intended binary explicitly when using a custom output folder:

```powershell
.\scripts\Verify-Localization.ps1 -Executable .\dist\v1.2.0\win-x64\CodexMonitor.exe
.\scripts\Verify-Published.ps1 -Executable .\dist\v1.2.0\win-x64\CodexMonitor.exe -OutputDirectory .\artifacts\verification\published-fr -UICulture fr-FR -SwitchLanguage
.\scripts\Verify-Published.ps1 -Executable .\dist\v1.2.0\win-x64\CodexMonitor.exe -OutputDirectory .\artifacts\verification\published-en -UICulture en-US
```

`Verify-Localization.ps1` runs offline native rendering and resource checks with an isolated copy of the EXE, testing French, English, and German fallback to English. External runtime discovery points to nonexistent paths. See the [localization test matrix](LOCALIZATION.md#rendering-and-verification).

`Verify-Published.ps1` needs an interactive Windows session, a signed-in Windows or WSL CLI, network access, and **no other running CodexMonitor instance**. Exit the installed instance before testing and restart it afterward. Its approximately 75-second live sequence opens the menu and details window, tests manual and automatic refresh, reconnection, stale/error presentation, duplicate rejection, and recovery of its own tray icon. Reports and targeted captures are saved before the diagnostic instance exits. It does not restart Explorer or change startup registration or saved preferences.

The executable diagnostic modes are `--verify-live <output-folder> [UI-culture] [--switch-language]` and `--verify-localization <culture> <output-folder>`. UI culture overrides affect only the diagnostic process. `-SwitchLanguage` adds live English → French → Automatic checks with cached errors and no extra quota read.

## Optional Windows UI Automation

With the intended monitor already running, the following developer checks inspect its real Explorer icon and details window:

```powershell
.\scripts\Verify-ShellBadge.ps1 -UICulture en-US
.\scripts\Verify-DetailsWindow.ps1 -UICulture en-US -RequireNoScrollbar
```

Use the actual interface culture (`fr-FR` for French). The shell check opens the notification overflow; the details check invokes the native Refresh button. These developer scripts load UI Automation assemblies from the installed Windows Desktop runtime supplied with the SDK. This developer requirement does not apply to normal executable use.

`Verify-LanguageSwitch.ps1` exercises the actual three language submenu options through UI Automation on a `--verify-live` instance, after its initial checks (about 20 seconds). In a second PowerShell session, supply its process ID and `session.json`:

```powershell
.\scripts\Verify-LanguageSwitch.ps1 -MonitorProcessId $diagnosticProcessId -OutputDirectory .\artifacts\verification\interactive-switch -SessionReport .\artifacts\verification\published-en\session.json -WindowsUICulture en-US
```

Set `$diagnosticProcessId` to the diagnostic monitor's process ID before running this command. The script verifies window ownership before interaction and closes the details panel afterward. Diagnostic choices are not saved to user settings. Avoid unrelated refresh clicks during timed live checks: a manual refresh moves the next automatic reading's deadline.

## Artifacts and delivery status

Executables, SDK caches, and detailed verification reports under `dist/` and `artifacts/` are ignored by Git and recreated by the scripts. Small documentation screenshots under `docs/images/` are retained separately. Their provenance is recorded in [TEST-RESULTS.md](TEST-RESULTS.md#documentation-screenshots).

The build version is 1.2.0; assembly metadata, About, details, and the App Server handshake use that shared version. Release binaries are built from the exact annotated tag, verified, and distributed through [GitHub Releases](https://github.com/Patrice-Gaudicheau/CodexMonitor/releases/latest) with `SHA256SUMS.txt`, `LICENSE`, and `THIRD-PARTY-NOTICES.txt`. The previous v1.0.0 and v1.1.0 releases and tags remain unchanged.
